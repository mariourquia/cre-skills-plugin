# v5.0.0 — Trust hardening + micro-skill architecture (consolidating v4.4.0 + v4.5.0)

## Summary

v5.0.0 is a single consolidating release. The source tree had been
version-stamped to 4.4.0 and then 4.5.0, but **neither tag was ever cut** — the
last published git tag is `v4.3.0`. This release folds all of that work, plus a
focused trust-hardening pass and a new micro-skill governance architecture, into
one honest, tagged `v5.0.0`.

It is deliberately conservative about what it claims. The headline is not "more
skills" — the catalog count (127 skills / 54 agents / 21 MCP tools / 10
orchestrators / 6 workflow chains) is unchanged from the 4.5.0 source state, and
**zero new stub skills** were added in the v5 modernization. The headline is
that the things the plugin already shipped are now **correct against current law,
honest about their data grade, and governable by an agent ecosystem.**

If a v5 marketing or collateral piece implies more than this document and
[`docs/known-limitations.md`](../known-limitations.md), the collateral is wrong.

## (a) Trust hardening — correctness, honesty, and refusal

The substance of why this is a major version. Four workstreams, each landed with
tests.

### Tax + climate corrected to current law

Three skills carried tax and climate guidance that the statute had moved past.
All three now model **current law**, reach the v5 skill contract
(`v5_contract: true`) with a `statute_review` horizon and advisory stamps, and
recompute their worked examples:

- **`opportunity-zone-underwriter`** — now models **both OZ regimes by
  investment date**: the pre-2027 legacy regime (fixed `12/31/2026` inclusion
  event) **and** the post-2026 **OBBBA permanent** regime (rolling 5-year
  deferral, restored 10% / 30%-rural basis step-ups, 2027 decennial zone maps).
  Previously it modeled only the expiring legacy regime.
- **`cost-segregation-analyzer`** — the dead TCJA bonus-depreciation phasedown
  (60 / 40 / 0) is replaced with the **OBBBA permanent 100% bonus** for property
  placed in service after `2025-01-19`. The PV-of-acceleration worked example is
  recomputed.
- **`climate-risk-assessment`** — re-anchored from **TCFD (disbanded 2023)** to
  **IFRS S2 (ISSB)** as the live disclosure framework.

These are advisory tools, not tax or legal advice; the corrected skills say so
and carry a re-verification horizon so the next statute change is caught.

### Calculators: typed refusal on degenerate input + a waterfall fix

The Python calculators now **refuse loudly instead of returning a misleading
number** on degenerate input, via a shared typed refusal envelope across
`debt_sizing`, `waterfall_calculator`, `covenant_tester`, `monte_carlo_simulator`,
`npv_trade_out`, `option_valuation`, `construction_estimator`, and
`tenant_credit_scorer`. Concretely: `debt_sizing` refuses non-positive NOI, and
`monte_carlo_simulator` refuses `trials < 1` (a case previously tracked as an
xfail DEFECT, now a real pass).

One correctness fix: the **JV waterfall catch-up base** previously included
return-of-capital. It no longer does (catch-up is computed on profit above the
preferred return, not on capital returned), and the tier is **relabeled
screening-grade** rather than implying a closing-ready promote calculation. New
behavioral tests cover the refusal contracts and `fund_fee_modeler` (which had no
behavioral tests before), plus a cross-cutting degenerate-input contract test.

### Privacy / feedback default reconciled to the truth

Older docs asserted a `local_only` feedback default. **The code default is
`ask_each_time`** (the plugin prompts for consent per submission and sends
nothing remotely without it). PRIVACY.md, MIGRATION.md, the CHANGELOG, and the
v4.0.0 notes are corrected to state the true default while preserving the
**separate** opt-out usage-telemetry language (anonymous, local-only telemetry is
a different mechanism from feedback submission). This was a documentation
correctness defect, not a behavior change.

### Installer + doc counts corrected

User-visible banners and post-install verification steps across `Install.command`,
`scripts/Install.ps1`, `scripts/create-dmg.sh`, `scripts/create-exe.iss`, and
`scripts/install.sh` advertised stale counts (105 / 113 skills). They now state
the live **127 skills / 54 agents / 21 MCP tools**. `docs/COMPATIBILITY.md` is
corrected to 127 / 21 and backed by a guard test. The release-version parity test
was tightened to **compute the live filesystem skill count** rather than assert a
hard-coded literal, so this class of drift fails CI going forward.

## (b) v5 micro-skill architecture

A governance layer that distinguishes a conductor from an atomic tool and carries
the metadata an agent ecosystem (notably AMOS) needs — added **additively**, with
no skill renamed and no frontmatter migration forced.

### Classification taxonomy + governance metadata

The catalog `CatalogItem` schema gains optional, backward-compatible fields:
`classification` (`micro` / `normal` / `orchestrator` / `workspace`),
`runtime_role`, `decision_grade`, `human_gate`, `source_ref_policy`,
`amos_surface`, `decomposes_to`, and `composed_from`. `catalog-build.py` reads,
derives, and emits them across all six item builders — including a
`final_marked → decision_grade` projection that reuses the existing contract
signal rather than renaming any frontmatter.

### A validator that actually validates the catalog

`tests/test_skill_classification.py` is new and does two things nothing did
before: it **jsonschema-validates the generated catalog**, and it **enforces the
governance rules** (decision-grade ⇒ human gate, source-ref policy present, etc.)
on an explicit allowlist of decision-grade / AMOS-facing slugs. This closes the
omission hole where governance metadata could be wrong and nothing caught it.

### 8 mega-skills reclassified, 0 new stubs

The 8 priority "mega-skills" are reclassified as `orchestrator` / `workspace` /
`normal` (they are conductors and routers, not atomic tools), and the
decision-grade / AMOS-facing pilot slice is annotated. `residential_multifamily`
is reclassified `workspace` (a one-line metadata change; its status and contract
machinery are untouched). The previously zero-reference `fund-lp-reporting` skill
gains a `routing-logic.md` that names its frameworks (ILPA, NCREIF-PREA). **No new
skill stubs were created** in this work.

### AMOS skill-manifest export

`dist/amos-skill-manifest.json` is a new **generated** export — a governed
superset of the catalog — that lets AMOS consume the plugin as a skill layer
without hardcoding each skill. It carries two code-computed crosswalks:
`runtime_role → AMOS demo status` (7 roles → 3 statuses) and
`human_gate → AMOS sign-off` (4 levels, including ADR-0004 debt/hedging
escalation). Its `generated_at` is deterministic (inherits the catalog timestamp;
`--as-of` overridable). The contract doc, JSON schema, and a tracked sample ship
in `docs/integrations/` (the build artifact itself lives under gitignored
`dist/`). 13 manifest tests back it.

## (c) Consolidated: the never-tagged v4.4.0 and v4.5.0 work

These two releases were version-stamped and shipped to `main` but never tagged.
Their release-note files remain `status: pending` by design — flipping them to
`released` would assert a tag that never existed. They are narrated here and ship
as part of `v5.0.0`. See [`docs/releases/v4.4.0-release-notes.md`](v4.4.0-release-notes.md)
and [`docs/releases/v4.5.0-release-notes.md`](v4.5.0-release-notes.md) for the
full detail.

### v4.4.0 — document → warehouse → deck skill chain (documentation-grade)

Three `reit-cre` skills that document the pipeline from extracted CRE documents
to institutional committee decks:

- **`document-to-warehouse-pipeline`** — orchestration above the single-document
  extractors; assembles extractor OUTPUT into validated, warehouse-ready tabular
  datasets with standardized provenance columns and a deck-readiness gate that
  surfaces (does not silently drop) failing rows.
- **`warehouse-to-exhibit-mapper`** — maps validated datasets to deck-ready
  exhibit specs, carrying provenance through so every exhibit cell keeps its
  `source_ref` + `classification`.
- **`ic-deck-composer`** — composes institutional committee decks (Investment
  Committee, Valuation Committee, Quarterly Business Plan / Asset Review, Annual
  Business Plan), executive-summary-first with an explicit decision ask.

**Honesty note:** these three GUIDE Claude. There is no database, charting
library, or slide renderer behind them; their output is a model-generated
specification a human reviews, not machine-validated output. Each SKILL.md says
so in its opening paragraph. In the v5 taxonomy `document-to-warehouse-pipeline`
is classified `orchestrator`.

### v4.5.0 — document-to-database ingestion family (executable)

Where the v4.4.0 chain guides, this family **executes**: it is backed by real,
deterministic, standard-library Python calculators that turn tokenized/extracted
CRE documents into validated, typed, auditable, target-model-ready database
payloads, and ties contractual rent-roll charges to T-12 account-level actuals.

- Skills: `document-to-database` (the orchestrator), `rent-roll-to-database`,
  `operating-statement-to-database` (the general root), `t12-to-database` (a
  constrained preset over it), and `rent-roll-t12-tieout` (basis-aware
  reconciliation that classifies mapping / timing / missing, surfaces
  `residual_unexplained`, and never forces a tie).
- Calculators in `src/calculators/`: `normalize_tokens`, `map_charge_codes`,
  `validate_payload`, `reconcile_rent_roll_t12`, `map_to_target_model`,
  `emit_sql_ddl`, `emit_load_plan`, `grade_ingestion`, `infer_schema`, plus a
  shared stdlib `ingest/` support package. Each is a pure
  `calculate_<x>(dict) -> dict`, byte-reproducible (no wall clock; `as_of` is
  caller-supplied), network-free, stdout-only.
- Governance: REUSES (does not fork) the residential-multifamily GL crosswalk +
  GL schema, the rent-roll `data-quality-rubric.yaml`, and the extractor's
  `pii-redaction-policy.yaml` (parity enforced by a sync test); a non-overridable
  PII-redaction-breach grade block; a weakest-link A/B/C grade. Five target-model
  profiles emit reviewable, DML-free Postgres DDL and a topologically-valid load
  plan (target-warehouse DDL, **not executed**).
- New ADR `docs/adr/0002-document-to-database-ingestion.md` and the
  `docs/ingestion/` documentation set.

## (d) Honest scope: read this before you act on any output

v5.0.0 separates what is decision-grade from what is not. The single canonical
data-grade ladder is [`docs/DATA_GRADES.md`](../DATA_GRADES.md); the per-vendor
connector truth is [`docs/connectors/CAPABILITY-MATRIX.md`](../connectors/CAPABILITY-MATRIX.md);
the full long-form statement is [`docs/known-limitations.md`](../known-limitations.md).

### What is decision-grade

- The **document-to-database ingestion family** is deterministic, typed, and
  auditable on the inputs it is given, with a weakest-link grade and a
  non-overridable PII-redaction block. It grades its own output and routes
  ambiguous items to human review.
- The **Python calculators** now refuse degenerate input rather than return a
  misleading figure. Outputs are screening- to analysis-grade and are labeled as
  such; they are not a substitute for a closing model or for tax/legal advice.
- Inside **`residential_multifamily`**, final-marked workflows enforce a
  source-class output contract, a period-seal gate, and refusal-on-missing-input
  — they fail closed rather than proceed on stale data.

### What is preview / staging

- **`residential_multifamily`** is `status: stable_pending_shakedown`
  (v1.0.0-rc1): code-complete with contracts active, but **every reference file
  still ships as sample / starter / illustrative / placeholder.** Decision-grade
  use requires an org overlay (the tailoring interview) to supply real data.
  Graduation to `status: stable` is gated on the first operator shakedown log
  (see [`docs/PREVIEW_MODE.md`](../PREVIEW_MODE.md)).
- The **document → warehouse → deck chain (v4.4.0)** is documentation-grade
  guidance, not a runtime. Treat its schemas, exhibit specs, and deck specs as
  proposed specifications requiring human review.

### What is connector-ready but NOT live

- **There is no live connector.** Every connector contract and every vendor
  adapter in the repo is `status: stub`. The only `active` ingestion shape is a
  shared-drive / email **file drop** (Excel / manual upload), not a live API
  feed. Per the capability matrix: CoStar is **not-supported-live** (its AI-use
  T&C); Yardi / MRI / RealPage are **blocked-by-vendor** pending sandbox access.
- The `source_class` provenance field and `max_staleness` consume-time refusal
  are **specified** (crosswalked in DATA_GRADES.md §2) but the connector runtime
  that emits and enforces them is **v5.1**.

### What requires org overlays

- Any decision-grade use of `residential_multifamily` requires the operator to
  run the tailoring interview and supply real org data; out of the box it carries
  placeholder overlays and will fail closed on final-marked paths.
- Firm-specific approval floors, charts of accounts, and benchmarks are supplied
  via overlays, not shipped in the plugin.

### Orchestration reality

- The orchestrator runtime `dispatchAgent()` is a **documented stub**. The real
  execution path is the **orchestrate prose** (`src/commands/orchestrate.md`):
  Claude acts as the conductor following documented phase + agent + verdict
  templates. Deal-state persistence, typed approval gates, and the calculator
  bridge have landed; full verdict aggregation and autonomous challenge-layer
  resolution remain in progress. Treat orchestrators as structured prompts, not
  fire-and-forget pipelines.

### Known Limitations

The authoritative list is [`docs/known-limitations.md`](../known-limitations.md).
In particular: no live connectors; the generalized cross-skill governance scanner
is **v5.1** (v5.0.0 ships the `final_marked` selector plus a **targeted**
finance-placeholder guard on a named allowlist, not a corpus-wide runtime
scanner); the four canonical connector contract schemas (`debt`, `entity`,
`valuation`, and promotion of `funds`) are **v5.1**; and the Windows `.exe` is
built on CI / Windows only (not locally buildable on macOS).

## Compatibility and breaking changes

No installed deployment breaks on upgrade. The "breaking" designation is honest
and minimal — see [`docs/MIGRATION.md`](../MIGRATION.md) for the v4.5.0 → v5.0.0
guide.

- **Additive metadata.** The v5 classification / governance fields are optional
  and backward-compatible; no skill was renamed and no frontmatter migration is
  required.
- **Calculator refusal envelope (behavior change).** Calculators that previously
  returned a (misleading) number on degenerate input now return a typed refusal.
  Any caller that depended on the old silent-number behavior must handle the
  refusal envelope.
- **JV waterfall catch-up (behavior change).** The catch-up base no longer
  includes return-of-capital, and the tier is relabeled screening-grade. Promote
  figures from the prior behavior will differ.
- **Feedback-default documentation correction.** The default was always
  `ask_each_time` in code; only the docs change. No runtime behavior changes.
- **Connector `source_class` hardening is deferred to v5.1.** v5.0.0 specifies
  the provenance + staleness contract; it does not yet enforce it at a connector
  runtime.
